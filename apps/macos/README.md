# SugarDash — native macOS dashboard for the Sugar work queue

A small, dependency-free SwiftUI app that talks to the local Sugar dashboard
backend over REST + Server-Sent Events. It is a **client of the database**, not a
second storage layer: `sugar/dashboard/` owns all writes, and the app simply
observes and edits through it.

Contract: [`docs/local-dashboard.md`](../../docs/local-dashboard.md) (frozen,
contract v1). Any disagreement between that document and this app is a bug in
the app.

## Requirements

- macOS 14 or newer (developed against macOS 26 / Swift 6.4, Xcode 27.1).
- The dashboard backend running locally:
  `pip install 'sugarai[dashboard]'`, then from your project directory:

  ```bash
  sugar dashboard          # http://127.0.0.1:7331 by default
  ```

  (Loopback only; v1 has no authentication.) Without the backend the app shows a
  clear empty state with the configured URL and a **Reconnect** button.
- No third-party Swift dependencies, no network access at build time.

## Build

```bash
cd apps/macos
swift build -c release      # plain SwiftPM build
./build-app.sh              # builds release + assembles dist/SugarDash.app
```

`build-app.sh` produces:

```
dist/SugarDash.app/
└── Contents/
    ├── Info.plist            # io.roboticforce.sugardash, minimum macOS 14.0
    ├── MacOS/SugarDash       # release binary
    └── Resources/
```

and ad-hoc signs it (`codesign -s -`). The bundle is launchable with
`open dist/SugarDash.app`; it is not notarized or signed with a Developer ID,
which is expected for a local/dev build.

## Distribution (DMG)

```bash
./build-dmg.sh --universal      # dist/SugarDash-<version>.dmg (arm64 + x86_64)
```

The DMG contains `SugarDash.app` plus an `Applications` symlink, so installing is
drag-and-drop. `build-app.sh` reads the version from the repo `pyproject.toml`
(the pre-release suffix is stripped for `CFBundleShortVersionString`), and the
DMG is named with the full version, e.g. `SugarDash-3.10.6.dev1.dmg`.

**Signing.** By default the app and DMG are ad-hoc signed. Recipients must
right-click the app and choose **Open** once (or run
`xattr -dr com.apple.quarantine /Applications/SugarDash.app`). For a warning-free
download, sign with an Apple Developer ID and notarize:

```bash
export SUGAR_CODESIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)"
export SUGAR_NOTARY_PROFILE="notary-profile"   # xcrun notarytool store-credentials …
./build-dmg.sh --universal --notarize
```

`--notarize` requires the keychain profile (app-specific password or API key,
stored by `notarytool store-credentials`); the script submits the DMG, waits for
the result and staples the ticket. Without a Developer ID certificate the build
still succeeds — it is simply ad-hoc.

The script also disables SwiftPM's manifest sandbox and points its caches at
`/tmp/sugar-swift-cache` (override with `SUGAR_SWIFT_CACHE=...`). Those flags make
the build reproducible in restricted environments (CI containers, agent
sandboxes) where nested sandboxes / the default clang module cache are denied.
They are harmless for normal local builds.

## About window and legal links

The app menu's **About SugarDash** item opens a proper About card (version + build,
website, docs, source, issue tracker, a one-line privacy statement, and
Copyright / AGPL / commercial-licensing lines). **Help** carries the same links
plus Privacy, Terms and a support email, and the menu bar extra has an About item
too.

`build-app.sh` writes `CFBundleDisplayName`, `NSHumanReadableCopyright`
(© 2026 RoboticForce Inc., AGPL-3.0) and
`NSApplicationCategoryType=public.app-category.developer-tools` into Info.plist.

The card links to <https://roboticforce.io/privacy> and
<https://roboticforce.io/terms>; keep those pages live before publishing a DMG.
"Copy diagnostics" copies version, macOS version, dashboard URL, connection state
and task count to the clipboard — nothing is sent anywhere.

## Feedback (explicit, never telemetry)

Help → **Send Feedback…** opens a form (Bug / Feature request / Other + message +
optional diagnostics). Nothing is sent automatically: you choose **Open GitHub
Issue** (public, prefilled, you review and submit) or **Send via Email** (private,
prefilled to `contact@roboticforce.io`), or copy the text. Long messages are
truncated in the URL and the full text is copied to the clipboard so nothing is
lost.

The optional diagnostics block contains app version, macOS version, dashboard URL,
connection state and task counts — never task titles, code, paths or credentials.
The only local record is a `feedback.submitted` event (category, destination,
message length) in the dashboard's activity spine, so the activity feed shows that
feedback was sent without storing the message.

## App icon

`Resources/AppIcon.icns` is generated by `make-icon.py` (Pillow): a coral→amber
squircle with a white rounded "S", legible from 16px to 1024px. Regenerate after
changing the design:

```bash
python3 make-icon.py --preview     # writes Resources/AppIcon.icns + /tmp preview
```

`build-app.sh` copies it into the bundle and sets `CFBundleIconFile`; the DMG
picker, Finder, Dock and About window all use it.

## Run

```bash
open dist/SugarDash.app
# or run the release binary directly (window + menu bar extra):
.build/release/SugarDash
```

The app opens one window:

- **Sidebar** — status filters (All / Pending / Active / Hold / Completed /
  Failed) with live counters, **Live** (agents at work), **Activity** (event
  feed), **Trends** (Charts analytics), the server URL field (persisted in
  `UserDefaults`), connection state, and the server's DB path/version. The last
  selected view (Tasks / Live / Activity / Trends) is persisted with
  `@AppStorage`, so relaunching the app returns to it (default: Tasks).
- **Task inspector** — the detail pane (`TaskDetailView`) is a native inspector
  that appears **only when a task is selected**; clearing the selection hides it and
  gives the width back to the task list / Live floor / Activity / Trends. A toolbar
  Inspector button (`sidebar.right`) toggles it while a task is selected. The task
  detail includes a **Live activity** strip (last 5 events for the task).
- **Live floor** — "Agents at work": one card per active task grouped by agent,
  with a pulsing lease-health dot (green > 60 s, amber < 60 s, red
  expired/missing), task title, **a live "current action" line** (the latest
  activity event for that task: message / command / tool + file, with kind icon
  and relative time; "waiting for activity…" after 120 s of quiet), "working for
  3m 12s", lease countdown and an attempts badge. Values tick every second via
  `TimelineView` (no network polling).
  The bottom strip is either the compact ticker (last 12 events) or the
  **Console**: a monospaced, streaming log (newest at the bottom, auto-follow
  until you scroll up, then "Jump to latest") with All / tool / run / task /
  memory filter chips and an "N ev/min" live rate. The header dot also pulses
  on each new event batch. Tapping a card, ticker row or console line jumps to
  the task. If the server doesn't emit the ephemeral `presence` event, the floor
  derives agents from active task leases and says so ("derived from task leases").
- **Trends** — Swift Charts analytics over `GET /api/trends`: 24h / 7d / 30d
  range + Agent / Project / Harness grouping, stat tiles (completed, failure
  rate, completed-weighted avg cycle time, cost, events), a line/area chart per
  group for Tasks completed / Tasks failed / Events / Cost with legend, x-axis
  labels and a hover tooltip, plus a per-group totals bar chart. Refreshes on
  range/dimension change and every ~30 s only while the pane is visible; shows
  clear empty, error and "older server (404)" states.
- **Task list** — priority, status, type, title, assigned agent, attempts and
  relative update time; searchable and filterable.
- **Detail** — a compact **Live activity** strip (last 5 events for the task,
  with kind icons, message and relative time) above the full task facts,
  description, context, acceptance criteria, result, error and thinking summary.
- **Toolbar** — New Task (⌘N), Refresh (⌘R), Reconnect, connection dot, and an
  "N agents working" chip that opens the Live floor.

Features:

- Live updates over SSE (`/api/events`); no polling loop. Reconnects with
  1 s → 10 s backoff and treats the new `snapshot` as authoritative.
- Ephemeral `presence` events drive the Live floor; presence is trusted for
  10 s, then the floor falls back to task leases (older servers never send it).
- Harness activity events (`tool.invoked`, `run.started`/`run.ended`,
  `agent.activity`, `memory.recalled`, `usage.reported`, …) drive each agent's
  current-action line, the Live console and the detail strip. Newest 500 events
  are kept in memory; the console shows exactly that window.
- Trends come from the optional `/api/trends` endpoint; servers that predate it
  (404) show an "isn't available on this server" state instead of an error.
  Trends are only fetched while the Trends view is visible (30 s cadence), and
  stale requests are cancelled/discarded when the range or dimension changes.
- Full CRUD: create, edit (including status transitions), hold/release, delete
  with a confirmation dialog.
- Type picker populated from `GET /api/task-types`; priority 1 (Urgent) – 5
  (Minimal).
- Read-only mode (`sugar dashboard --read-only`) is detected via `/api/health`
  and disables all write actions.
- Menu bar extra shows the pending count; its menu has Open Dashboard,
  Reconnect, and Quit.
- Unreachable server → empty state showing the URL + `sugar dashboard` hint +
  Reconnect.

## Tests

Decoding is covered by XCTest fixtures copied verbatim from the contract
(`Tests/SugarDashTests/DecodingTests.swift`): a null-heavy task, the SSE snapshot
with stats, and an ISO-8601 `Z` timestamp. `LiveTests.swift` covers the
`presence` payload (nulls, missing keys, unknown fields), lease-health
thresholds, actor grouping/order, the task-lease fallback, the live
formatting helpers, latest-action selection (task match / actor fallback /
120 s freshness), payload message extraction priority, console filtering /
ordering / rate math and the task-detail event selection; `TrendsTests.swift`
covers the `/api/trends` payload (full, tolerant, zero-filled alignment, empty),
range→since/until/bucket math with an injected clock, dimension/metric mapping,
failure-rate and weighted cycle-time aggregation, formatting, palette stability
and the persisted-view/query-key helpers; `ActivityTests.swift` covers the
event spine.

```bash
swift test
```

In a sandboxed/restricted shell, use the same flags as `build-app.sh`:

```bash
export CLANG_MODULE_CACHE_PATH=/tmp/sugar-swift-cache/clang
export SWIFT_MODULECACHE_PATH=/tmp/sugar-swift-cache/swift
swift test --disable-sandbox \
  --cache-path /tmp/sugar-swift-cache/spm \
  --config-path /tmp/sugar-swift-cache/spmconf
```

## Notes / v1 limitations

- One connection per app instance; no multi-server support.
- The board server now supports opt-in remote access with scoped bearer tokens
  (`--bind --allow-remote --token-file`), but the app has no token field yet, so it
  still expects a loopback/unauthenticated board. Remote TLS is terminated by a
  reverse proxy (see `docs/board-server.md`).
- "Hold" sends a fixed reason (`Held from the SugarDash app`); the v1 UI has no
  reason prompt.
- The editor's assigned-agent field sends `""` to clear an assignment (the
  contract does not define a dedicated clear semantics).
